# Memory architecture integration (experimental)

Independent of Global Replay. Default Muon-ME remains unchanged. Opt in with `momentum_storage=bf16`, `momentum_storage=int8 momentum_block=64`, or `momentum_storage=splitmax momentum_block=64` in Muon-ME optimizer arguments. FP32 factors required; arithmetic uses reconstructed FP32 state. Strict positive chunk budget; estimate excludes backend workspace and allocator residency. Direct compressed-state restoration validates shape, codec and payload before publication; matching parameter order required (names checked if present). Changing storage on resume is rejected; old/new packed states may overlap during restore. A partial failed update must not be retried.

CPU verification: 9 regression tests passed under PyTorch 2.10 CPU using the new module and a transcribed baseline Muon-ME implementation. Tested first step, resume, dtype, payload size, outlier/padding, malformed records and preflight. The factory reached real Krea 2 startup on the compressed arms, but no completed compressed CUDA update is verified; see the pilot history below. No production recommendation. Finite checking adds one host sync per chunk in compressed modes; measure it.

## Activation and telemetry integration

Explicit family options `geometry_memory_phase=peaks` (or `passive`), `geometry_activation_mib=512`, `geometry_host_floor_mib=6144`, `geometry_memory_require_h2d=1`. Eager full-checkpoint standard batch-1, accumulation-1 Krea 2 only. Actual offloader checked; no fallback allowed when requested. Synchronous full-storage contiguous inputs only, host capacity and available-RAM floor, no pinned or async copies. Backward-hook-created views are allowed; live aliases may reduce actual savings. CPU hook, RNG, host cap and mock telemetry tests pass (15 total including compressed optimizer). The first real Krea 2 synchronous activation-offload arm completed 13 updates, but forward telemetry was incomplete and paired numerical correctness remains unverified. Phase reset mode preserves training peak across phase resets and separates preview scope. Host elapsed is enqueue/wall timing, not exact GPU execution. Packed resume loads from CPU and validates stable parameter names. No production defaults changed.

## First GPU queue

In Start, select the same Krea 2 dataset used in the prior comparison and click **Test memory architecture**. Five fresh runs, rank/alpha 64, swap 22, target 0.25 MP, fixed 192 MiB scratch estimate (revised from 128 MiB at d7df5b3), seed 42, holdout, eager full checkpointing, actual H2D-only ring required. Up to 20 updates or one epoch; no previews or exports. Control, BF16, INT8 block 64, Split-Max 64, synchronous input offload (512 MiB host cap, 6 GiB available RAM floor). Fixed controls disable automatic OOM recovery and VRAM reclaim. The final JSON includes phase maxima, state dtypes and storage, offload counts, transfer totals, and per-step losses (added at 1ff0c21). A finished exit without matched telemetry or an actual offload is not counted as a successful arm. Short queue is feasibility only, not a learning-quality gate. Run separately before any swap 20/21, combined, or 1 MP experiments. CPU tests exercise pure queue flags/settings and telemetry parsing, not the full web server or CUDA.

## Optional automatic scratch budgeting

`auto_memory_budget=True memory_reserve_mib=768 memory_growth_steps=3` is an opt-in Muon-ME argument set (FP32 and compressed state modes). The existing positive `chunk_memory_mib` remains a hard estimated ceiling. Driver-free bytes are sampled before updates, missing persistent state is reserved, and the allowance decreases immediately and grows after consecutive sufficient snapshots. No allocator cache credit, device paging guarantee, or automatic retry. Compressed cold-step planning conservatively includes replacement overlap as well as new persistent payload. The per-device hysteresis policy starts fresh on process restart; state serialization preserves momentum, not a transient VRAM snapshot. The first five-arm GPU queue deliberately leaves auto budgeting disabled. PoLoRA and TSD integration still requires optimizer-specific scratch estimates and GPU evidence. Seven new standalone CPU cases passed at the budgeting milestone, bringing the reported local regression total to 24. The revised cap regression milestone reported 27 standalone passes; full CUDA budgeting, compressed resume, and trainer correctness remain unverified.

## Pilot fixes and current protocol (2026-11-27)

[Historical pilot results](MEMORY_ARCHITECTURE_GPU_PILOT_20261125.md). The original 128 MiB queue is superseded, not the general default for ordinary Muon-ME. Existing queued entries should not be reused. A new queue sets 192 MiB for all five cases. The compressed optimizer now checks actual factor shapes before training and reports required/allowed scratch in MiB; `ScratchBudgetError` indicates policy refusal, not a failed allocation. The largest modeled Krea 2 rank64 factor is 36864 × 64; estimated scratch requirements are BF16 157.55 MiB, INT8 155.44 MiB, Split-Max 155.61 MiB. These estimates are not CUDA peaks. At d7df5b3 the three full-size CPU cases exercised two updates per mode at 192 MiB and rejection at 128 MiB; 27 standalone tests were reported passed. No new test execution in this documentation update.

Future correctness/quality protocol: repeat FP32 control to estimate variation, verify paired initialization and actual input/noise/conditioning/timestep identity, compare fixed-input loss/gradients and effective adapter updates, then test extended learning and resume. Borrow the existing LittleBit observer and compact geometry diagnostics where appropriate after source review; do not enable these or any cross-branch optimizer/selection changes in the current feasibility queue. Separate instrumentation overhead from clean timing.
